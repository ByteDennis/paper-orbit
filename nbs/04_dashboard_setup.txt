DTRACK COUNT WATCH DASHBOARD SETUP
==================================

Purpose
-------

Create one Databricks AI/BI dashboard backed directly by the Delta table created
by 02_dbx_count_watch.ipynb. The dashboard shows recent partition-count checks by
default while retaining configuration snapshots and full historical details for
download.

The Delta table remains the source of truth. The dashboard is a presentation
layer only. Local and Databricks jobs must read the table, not the dashboard.


Prerequisites
-------------

1. Run the CREATE TABLE cell in 02_dbx_count_watch.ipynb once.
2. Replace every <catalog>.<schema>.table_list placeholder with the real table.
3. Confirm that the dashboard owner can use a SQL warehouse and SELECT the table.
4. Confirm that maintainers who change review_status can UPDATE the table.
5. Never store passwords, tokens, secrets, or DSNs in either connection JSON.


1. Create the dashboard
-----------------------

1. Open Databricks SQL.
2. Open Dashboards and choose Create dashboard.
3. Name it "DTrack Count Watch".
4. Attach the SQL warehouse that should run the dashboard datasets.
5. Use the publisher's data permissions only if every intended viewer is allowed
   to see the data exposed by both dashboard pages.


2. Create the default history dataset
-------------------------------------

Create a dataset named pair_check_history with this query:

SELECT
  query_date,
  pair_name,
  config_version,
  aws_name,
  offset_days,
  left_partition,
  right_partition,
  left_count,
  right_count,
  count_state,
  review_status,
  left_checked_at,
  right_checked_at,
  error_message
FROM <catalog>.<schema>.table_list
WHERE query_date IS NOT NULL
ORDER BY query_date DESC, pair_name;

Do not add a fixed date predicate to the dataset. The dashboard date filter will
control the visible history without changing the underlying table.


3. Build the default Overview page
----------------------------------

1. Rename the first page "Overview".
2. Add a date filter bound to query_date.
3. Set its initial range to the most recent 7 days.
4. Add a table visualization using pair_check_history.
5. Show these columns in this order:

   query_date
   pair_name
   aws_name
   offset_days
   left_partition
   right_partition
   left_count
   right_count
   count_state
   review_status
   right_checked_at

6. Keep config_version and error_message available to the dataset, but omit them
   from the default table unless operational debugging requires them.
7. Apply status colors:

   SUCCESS             green
   FAIL                red
   ERROR               red
   WAITING_RIGHT       yellow
   PENDING_RIGHT       blue
   CHECKED_SUCCEEDED   green
   CHECKED_FAILED      red
   NOT_CHECKED         gray

8. Add KPI widgets if useful:

   total checks        count(*)
   successful          count_if(count_state = 'SUCCESS')
   failed              count_if(count_state IN ('FAIL', 'ERROR'))
   waiting             count_if(count_state IN ('PENDING_RIGHT', 'WAITING_RIGHT'))

Bind every widget to the query_date filter.


4. Add a Details and Download page
----------------------------------

Create a second dataset named pair_check_details from the same Delta table:

SELECT
  check_id,
  pair_name,
  config_version,
  query_date,
  timezone,
  review_status,
  offset_days,
  aws_name,
  left_query_variable,
  right_query_variable,
  left_conn_detail,
  right_conn_detail,
  left_partition,
  right_partition,
  left_count,
  right_count,
  count_state,
  left_checked_at,
  right_checked_at,
  error_message,
  created_at,
  updated_at
FROM <catalog>.<schema>.table_list
ORDER BY created_at DESC, pair_name;

1. Add a second dashboard page named "Details and Download".
2. Add filters for query_date, pair_name, count_state, and review_status.
3. Add a table visualization containing every dataset column.
4. Keep Overview as the default page so connection and query details are not
   shown during normal use.
5. Authorized editors can download the full dataset as CSV, TSV, or Excel from
   the dataset editor. If viewer data download is enabled, viewers can use the
   table widget menu on this page to download the filtered detail rows.

Download permissions are data permissions. Do not publish the detail page to
users who should not receive connection-routing metadata.


5. Human review-status workflow
-------------------------------

review_status is human-owned. Neither Notebook 01 nor Notebook 02 changes it.

Allowed values:

  NOT_CHECKED
  CHECKED_FAILED
  CHECKED_SUCCEEDED

To find the exact current row for one pair:

SELECT check_id, pair_name, config_version, review_status, count_state, created_at
FROM <catalog>.<schema>.table_list
WHERE pair_name = 'accounts'
ORDER BY config_version DESC, created_at DESC, check_id DESC
LIMIT 1;

After reviewing that row, update it by its exact check_id:

UPDATE <catalog>.<schema>.table_list
SET review_status = 'CHECKED_SUCCEEDED',
    updated_at = current_timestamp()
WHERE check_id = '<reviewed-check-id>';

Use CHECKED_FAILED when the pair still needs future daily checks. Once the latest
row is CHECKED_SUCCEEDED, Notebook 01 excludes the pair from future checks.


6. Configuration changes
------------------------

Do not rewrite historical check rows. To change a pair configuration:

1. Read the pair's latest row.
2. Insert a new configuration-only row.
3. Increment config_version.
4. Set query_date, partition values, counts, and checked timestamps to NULL.
5. Set review_status to NOT_CHECKED and count_state to NOT_RUN.
6. Use a new UUID for check_id.

The next local run selects the largest config_version and creates a daily check
from that snapshot. See the insert example in 02_dbx_count_watch.ipynb and the
logical JSON shape in table_list.example.json.


7. Publish and validate
-----------------------

1. Publish the dashboard.
2. Open the published view as a normal viewer.
3. Confirm that Overview initially shows only the most recent 7 days.
4. Change the date filter and verify older history appears.
5. Confirm that CHECKED_SUCCEEDED pairs remain visible historically.
6. Confirm that the Details and Download page exposes the expected filtered rows.
7. Download a detail export and verify that both connection JSON fields and both
   query-variable fields are present.
8. Confirm that no exported JSON contains credentials, tokens, passwords, or DSNs.
9. Run Notebook 01, then Notebook 02, and refresh the dashboard to verify that a
   new historical row moves from PENDING_RIGHT to its final count_state.


Operational order
-----------------

1. Human maintains configuration snapshots and review_status in the Delta table.
2. Local Notebook 01 runs first and writes the Left daily check row.
3. Databricks Notebook 02 runs afterward and fills the Right result.
4. The dashboard refreshes from the same table.
5. Human review can mark the latest row CHECKED_SUCCEEDED to retire the pair.
